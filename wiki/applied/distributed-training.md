## Общая ментальная модель
Distributed training обычно выглядит так:
1. Запускается несколько независимых процессов.
2. Каждый процесс получает собственный идентификатор — `rank`.
3. Процессы находят друг друга и между ними создаётся канал коммуникации.
4. Каждый процесс выполняет одну и ту же программу над своей частью данных - Single Program, Multiple Data
5. В определённых точках процессы обмениваются тензорами через collective operations.

![[mental_model.png|725]]

## Process, rank, local rank и world size
**Process — это обычный процесс операционной системы**, запустивший Python-программу обучения. У каждого процесса есть собственные Python interpreter, CUDA context, память CPU, экземпляр модели, optimizer.
В типичной конфигурации 1 Process ↔ 1 GPU. Но это соглашение, а не фундаментальное правило. Теоретически процесс может работать без GPU, с несколькими GPU и даже на той же GPU, что и другой процесс. Однако вариант с одним процессом на одну GPU наиболее распространённый и безопасный .

**World size — количество процессов, участвующих в группе.** 
World size считает именно **процессы**, а не машины или GPU как физические устройства. 

**Rank — это глобальный идентификатор процесса внутри process group.**
Нужно помнить, что **Rank 0 — это не обязательно «главный процесс»**. У `rank 0` нет фундаментально более высоких прав. Это обычный участник группы, которому по соглашению часто поручают вывод логов, запись чекпоинтов и тд.

**Local rank — это идентификатор процесса в пределах одной машины.** 
Таким образом, rank - уникален во всей distributed job, а local_rank - уникален только внутри конкретной ноды.

## Process group

**Process group — это набор процессов, которые могут обмениваться данными и совместно выполнять collective operations.** Она задаёт границы коммуникации: операция выполняется не просто между какими-то запущенными процессами, а между участниками конкретной группы.

У каждой process group есть собственный набор участников. Они задаются через глобальные `rank`: например, группа может включать все процессы или только часть из них — допустим, ranks `[0, 1, 2, 3]`. Размер группы определяется числом её участников и не обязательно совпадает с глобальным `world_size`.

Например, вызов:

```python
dist.all_reduce(tensor, group=my_group)
```

означает, что `all_reduce` должны выполнить все процессы, rank которых входят в `my_group`. Процессы, которые не являются участниками этой группы, в операции не участвуют.

Process group хранит не только список ranks. С ней также связаны communication backend, timeout и внутренние объекты коммуникации, через которые процессы устанавливают соединения и обмениваются тензорами. Для NCCL таким внутренним объектом является NCCL communicator. Обычно разработчик не работает с ним напрямую: PyTorch создаёт и использует его внутри реализации process group.

Таким образом, process group можно воспринимать как **контекст коммуникации**. Она определяет, какие процессы должны участвовать в операции и какой механизм связи будет использоваться для передачи данных между ними.

#### Default process group
В начале distributed-программы обычно вызывается:

```python
dist.init_process_group(backend="nccl")
```

Этот вызов инициализирует основную process group, которую называют **default process group** или **WORLD group**. Как правило, в неё входят все процессы текущего distributed job: ranks = {0, 1, ..., world_size - 1}

Именно относительно этой группы определяются глобальные `rank` и `world_size`. Например, если были запущены восемь процессов, то WORLD group обычно содержит ranks от `0` до `7`, а её размер равен `8`.

Дополнительные process groups нужны, когда обмен должен происходить не между всеми процессами job, а только между определённым подмножеством. Например, в сложном параллельном обучении отдельные группы могут использоваться для data parallelism, tensor parallelism или pipeline parallelism. При этом WORLD group продолжает существовать как общая группа, объединяющая все процессы.

## Rendezvous и инициализация

Rendezvous и инициализацию process group полезно рассматривать как два связанных, но разных этапа.
### Rendezvous

**Rendezvous — это этап, на котором процессы distributed job находят друг друга и формируют общее представление о составе джобы.** До этого момента каждый процесс запущен независимо и ещё не знает, с какими другими процессами ему предстоит работать.

Чтобы начать распределённое выполнение, все процессы должны согласовать несколько базовых параметров: сколько всего участников входит в job, какой `rank` принадлежит каждому из них и через какую точку они смогут обменяться информацией, необходимой для установления соединений. На основе результатов rendezvous PyTorch затем создаёт default process group и внутренние объекты коммуникации выбранного бекенда.

В обычном статическом запуске состав job заранее известен и не меняется. Например, `torchrun` запускает заданное количество процессов и передаёт каждому из них необходимые параметры (как минимум RANK, WORLD_SIZE, MASTER_ADDR  и MASTER_PORT) через environment variables. `MASTER_ADDR` и `MASTER_PORT` указывают адрес координационной точки, через которую процессы обмениваются служебной информацией во время инициализации.
### Инициализация process group

После того как processes нашли друг друга, каждый из них вызывает:

```python
dist.init_process_group(backend="nccl")
```

Этот вызов создаёт default process group и инициализирует communication backend. PyTorch поддерживает инициализацию через явно переданные `store`, `rank`, `world_size` либо через `init_method`; если ничего не указано, используется `env://`.

Упрощённая последовательность:

```text
1. Launcher запускает процессы.
2. Rendezvous определяет участников. Каждому процессу назначаются rank и world_size.
3. Процессы получают общий rendezvous/store endpoint.
4. init_process_group создаёт WORLD process group.
5. Backend создаёт communicators и соединения.
6. Начинается исполнения программы.
```

## Single Program, Multiple Data

**SPMD — это модель исполнения, при которой все процессы запускают одну и ту же программу, но работают каждый над своей частью данных.** Именно поэтому `torchrun` запускает один и тот же скрипт на всех рангах без изменений: различие между процессами задаётся значениями `rank`, `local_rank` и тем, какой шард данных достался процессу.

Важно не путать SPMD с SIMD. **SIMD** (Single Instruction, Multiple Data) — это про синхронность на **уровне инструкций**: одна и та же инструкция в один и тот же момент применяется сразу к нескольким элементам данных. **SPMD говорит только про одинаковый текст программы.** Все процессы запускают один и тот же файл, но дальше исполняют его самостоятельно: у каждого свой program counter, свой стек, свои локальные переменные. Никто не заставляет их находиться в одной и той же строке в один и тот же момент.

Поэтому в реальности ранги почти всегда рассинхронизированы во времени. Один процесс может уже досчитывать forward третьего слоя, пока другой ещё только загружает батч — просто потому, что ему достался медленный диск или GPU чуть сильнее нагрета. Это нормально и само по себе не является ошибкой.

Синхронизация возникает только в явных точках — при вызове collective operation. Процесс, дошедший до `all_reduce` первым, останавливается и ждёт остальных участников группы. Между такими точками процессы живут независимо. Отсюда и вытекает главное следствие: программа одна, а траектории исполнения независимы.

![[spmd.png]]

Полезно различать два вида дивергенции:
**Безопасная дивергенция** — ветвление по `rank`, внутри которого нет collective operations:
```python
if rank == 0:
    logger.info(f"step={step} loss={loss.item():.4f}")
    save_checkpoint(model, path)
```
   	
**Опасная дивергенция** — ветвление по данным. Условие вычисляется из локального шарда, поэтому у разных процессов оно может дать разный результат:
```python
if loss.isnan():   # у rank 3 True, у остальных False
    break          # rank 3 выходит из цикла, остальные ждут его в all_reduce
```

Отсюда общее правило: **любое решение, влияющее на поток управления, должно быть согласовано между процессами явно** — то есть само пройти через collective operation.
## Point-to-point communication
**Point-to-point communication — это прямая передача данных между двумя конкретными процессами:** один процесс выступает отправителем, а другой — получателем. 
В такой коммуникации не обязаны участвовать все процессы группы. Например, rank 0 может отправить тензор rank 1, пока rank 2 и rank 3 продолжают выполнять другой код.

```
rank0: [A] ── send ──► rank1: [?] → [A]
rank2:               выполняет другой код
rank3:               выполняет другой код
```

При этом вызовы должны быть согласованы между участниками обмена: каждому `send` должен соответствовать подходящий `recv`. Отправитель и получатель должны указать друг друга, а принимающий буфер должен быть совместим с передаваемым тензором.
#### Send и Recv
`send` отправляет тензор процессу `dst`, а `recv` записывает полученные данные в заранее созданный буфер.

```python
if rank == 0:
    tensor = torch.tensor([1, 2, 3], device=device)
    dist.send(tensor, dst=1)

elif rank == 1:
    tensor = torch.empty(3, device=device, dtype=torch.int64)
    dist.recv(tensor, src=0)
```

```
до:     rank0: [1, 2, 3]    rank1: [?, ?, ?]
после:  rank0: [1, 2, 3]    rank1: [1, 2, 3]
```

`send` и `recv` являются блокирующими. Каждой отправке должен соответствовать приём с совместимым размером и типом тензора. Несогласованный порядок операций может привести к deadlock.

```
rank0: send → ждёт rank1 ─┐
                          ├─ deadlock
rank1: send → ждёт rank0 ─┘
```

Для неблокирующей передачи используются `isend` и `irecv`. Они возвращают объект `Work`, завершения которого можно дождаться через `wait()`.

```
send_work = dist.isend(send_tensor, dst=1)
recv_work = dist.irecv(recv_tensor, src=1)

# Независимые вычисления

send_work.wait()
recv_work.wait()
```

**Примеры использования:**
- передача activations и gradients между стадиями pipeline parallelism;
- пользовательские схемы model parallelism.
## Collective operations
**Collective operation — это операция коммуникации, в которой участвуют все процессы process group.** Это не обмен между двумя конкретными процессами, а заранее известный шаблон взаимодействия: каждый процесс передаёт данные, получает их либо делает и то и другое.

![[collective_ops.png]]

Ключевое требование: **все участники process group должны вызвать совместимые collective operations в одинаковом порядке**. Например, если rank 0 вызывает `all_reduce`, а rank 1 в этой же позиции вызывает `broadcast` или вообще не доходит до коммуникации, выполнение зависнет либо завершится ошибкой после timeout.

Некоторые операции используют выделенный процесс:
- `src`, или source, — процесс, который отправляет исходные данные;
- `dst`, или destination, — процесс, который получает итоговый результат;
Процесс, выполняющий роль источника или получателя в зависимости от операции, часто называют **root**.
#### Broadcast
**Broadcast передаёт тензор одного процесса всем остальным процессам группы.** Исходный тензор находится на `src`, а тензоры остальных процессов используются как принимающие буферы. После завершения операции во всех них находятся одинаковые данные. Операция выполняется in-place. Все участвующие процессы должны передать тензоры с одинаковым количеством элементов.

```python
dist.broadcast(tensor, src=0)
```

```
до:     rank0: [A]   rank1: [?]   rank2: [?]   rank3: [?]
после:  rank0: [A]   rank1: [A]   rank2: [A]   rank3: [A]
```
Знак `?` не обязательно означает неинициализированную память. Значение может быть любым — оно будет перезаписано данными rank 0.

**Примеры использования:**
- Синхронизация начального состояния модели. При создании DDP с `init_sync=True` параметры и буферы передаются с одного ранга остальным, чтобы все реплики начали обучение с одинакового состояния.
- Распространение решения, принятого rank 0. Например, rank 0 может выбрать checkpoint, сгенерировать seed или вычислить новый learning rate, после чего передать значение всем процессам.

```python
if rank == 0: 
	seed = torch.tensor([12345], device=device, dtype=torch.int64) 
else: 
	seed = torch.empty(1, device=device, dtype=torch.int64) 

dist.broadcast(seed, src=0) 
torch.manual_seed(seed.item())
```

#### Reduce
Reduce поэлементно объединяет тензоры всех процессов и сохраняет результат только на процессе dst. Способ объединения задаётся аргументом `op`: это может быть сумма, минимум, максимум, произведение и другие reduction operations. Операция выполняется in-place: на `dst` исходный тензор перезаписывается результатом.

```python
dist.reduce(tensor, dst=0, op=dist.ReduceOp.SUM)
```

```
до:     rank0: [1]    rank1: [2]    rank2: [3]    rank3: [4]
SUM:                   1 + 2 + 3 + 4 = 10
после:  rank0: [10]   rank1: [—]    rank2: [—]    rank3: [—]
```

**Примеры использования:**
- Сбор метрик только на rank 0. Каждый процесс считает сумму loss и количество обработанных объектов, после чего rank 0 вычисляет глобальное среднее.
- Сбор общего количества ошибок, пропущенных батчей или обработанных токенов для логирования.

```python
stats = torch.tensor( [local_loss_sum, local_num_samples], device=device, dtype=torch.float64) 

dist.reduce(stats, dst=0, op=dist.ReduceOp.SUM) 

if rank == 0: 
	global_mean_loss = (stats[0] / stats[1]).item()
	print(f"loss: {global_mean_loss:.4f}")
```

#### All-Reduce
All-Reduce поэлементно объединяет тензоры всех процессов и возвращает одинаковый результат каждому процессу. Операция выполняется in-place: исходный тензор каждого процесса заменяется результатом reduction.

```python
dist.reduce(tensor, op=dist.ReduceOp.SUM)
```

```
до:     rank0: [1]    rank1: [2]    rank2: [3]    rank3: [4]
SUM:                   1 + 2 + 3 + 4 = 10
после:  rank0: [10]   rank1: [10]   rank2: [10]   rank3: [10]
```

По семантике `all_reduce` можно представить как `reduce` с последующим `broadcast`, однако реальная реализация не обязана буквально выполнять эти две операции.

**Примеры использования:**
- Синхронизация градиентов в DDP. Когда градиенты bucket становятся готовы, DDP запускает для них `all_reduce`, после чего соответствующие градиенты одинаковы на всех репликах модели.

```python
dist.all_reduce(gradient, op=dist.ReduceOp.SUM)
gradient.div_(world_size)
```
PyTorch также предоставляет `ReduceOp.AVG`, но его поддержка зависит от backend и версии NCCL. Поэтому явные `SUM` и деление обычно делают поведение кода более очевидным и переносимым.
#### Gather
Gather собирает тензоры всех процессов на одном процессе dst. Данные не объединяются арифметически: тензор каждого rank помещается в отдельную позицию списка `gather_list`. Порядок элементов соответствует rank процессов.

```python
gather_list = [torch.empty_like(tensor) for _ in range(world_size)] if rank == 0 else None
dist.gather(tensor, gather_list=gather_list, dst=0)
```

```
до:       rank0: [A]   rank1: [B]   rank2: [C]   rank3: [D]

после:    rank0: gather_list = [[A], [B], [C], [D]]
          rank1: gather_list = None
          rank2: gather_list = None
          rank3: gather_list = None
```

`gather_list` создаётся только на `dst`. На остальных процессах он должен быть равен `None`. Все передаваемые тензоры должны иметь одинаковый размер.

В актуальном PyTorch NCCL поддерживает `gather` для CUDA-тензоров. Тем не менее в distributed training чаще встречается `all_gather`: результат нередко нужен не только rank 0, а специализированные distributed-алгоритмы обычно строятся вокруг симметричных collective operations.

#### All-Gather
All-Gather собирает тензоры всех процессов и передаёт полный список каждому процессу. После завершения операции все процессы имеют одинаковый `output`, содержащий данные rank в порядке их номеров.

```python
output = [ torch.empty_like(tensor) for _ in range(world_size) ]
dist.all_gather(output, tensor)
```

```
до:     rank0: [A]   rank1: [B]   rank2: [C]   rank3: [D]

после:  rank0: [[A], [B], [C], [D]]
        rank1: [[A], [B], [C], [D]]
        rank2: [[A], [B], [C], [D]]
        rank3: [[A], [B], [C], [D]]
```

В отличие от обычного `gather`, актуальная реализация `all_gather` поддерживает тензоры разного размера. При этом каждый процесс должен заранее создать выходные буферы правильных размеров.

**Примеры использования:**
- Сбор embeddings со всех GPU в contrastive learning. Локальные embeddings других процессов становятся дополнительными positive или negative examples.
- Восстановление полного параметра из шардов перед вычислением слоя в FSDP.

```python
local_embeddings = encoder(local_batch)

gathered_embeddings = [
    torch.empty_like(local_embeddings)
    for _ in range(world_size)
]

dist.all_gather(gathered_embeddings, local_embeddings)

global_embeddings = torch.cat(gathered_embeddings, dim=0)
```

Основной недостаток — расход памяти. Если локальный тензор занимает `M` байт, после `all_gather` каждый процесс хранит примерно `world_size × M` байт данных.
#### Scatter
Scatter раздаёт процессам элементы списка, находящегося на `src`. Каждый процесс получает ровно один тензор: rank `i` получает `scatter_list[i]`. Полученный результат записывается в переданный выходной тензор.

```python
scatter_list = [t0, t1, t2, t3] if rank == 0 else None
dist.scatter(tensor, scatter_list=scatter_list, src=0)
```

```
до:     rank0: scatter_list = [[A], [B], [C], [D]]
        rank1: None
        rank2: None
        rank3: None

после:  rank0: [A]   rank1: [B]   rank2: [C]   rank3: [D]
```

**Примеры использования:**
- Распределение заранее подготовленных шардов параметров или optimizer state.
- Раздача разных входных тензоров, если они были созданы или загружены только rank 0.
#### Reduce-Scatter
Reduce-Scatter сначала поэлементно объединяет данные всех процессов, а затем разделяет результат на шарды. Rank `i` получает только `i`-й шард итогового тензора, а не полный результат.

Удобно считать, что вход каждого процесса заранее разделён на `world_size` частей:

```
до:
rank0: [A0 | A1 | A2 | A3]
rank1: [B0 | B1 | B2 | B3]
rank2: [C0 | C1 | C2 | C3]
rank3: [D0 | D1 | D2 | D3]

после SUM:
rank0: [A0+B0+C0+D0]
rank1: [A1+B1+C1+D1]
rank2: [A2+B2+C2+D2]
rank3: [A3+B3+C3+D3]
```

```python
dist.reduce_scatter_tensor(output, input_tensor, op=dist.ReduceOp.SUM)
```

**Примеры использования:**

- Синхронизация sharded-градиентов в FSDP. Градиенты суммируются между процессами, но каждый rank сохраняет только градиент своего шарда параметров.
- Реализация ZeRO, где optimizer state и градиенты распределены между процессами.

Для равномерно разделённых данных `all_reduce` можно алгоритмически разложить на две стадии:

```
all_reduce = reduce_scatter + all_gather
```

Сначала процессы вычисляют разные шарды итоговой суммы, затем обмениваются ими через `all_gather`.
#### All-to-All
All-to-All позволяет каждому процессу отправить отдельный кусок данных каждому другому процессу. Вход каждого rank делится на `world_size` частей. Часть с индексом `i` отправляется процессу с rank `i`, после чего каждый процесс объединяет полученные от всех rank части.

```python
dist.all_to_all_single(output, input_tensor)
```

При равных размерах частей операцию удобно представить как транспонирование матрицы:

```
до:
rank0: [A0 | A1 | A2 | A3]
rank1: [B0 | B1 | B2 | B3]
rank2: [C0 | C1 | C2 | C3]
rank3: [D0 | D1 | D2 | D3]

после:
rank0: [A0 | B0 | C0 | D0]
rank1: [A1 | B1 | C1 | D1]
rank2: [A2 | B2 | C2 | D2]
rank3: [A3 | B3 | C3 | D3]
```

**Примеры использования:**

- Маршрутизация токенов в Mixture of Experts. Каждый процесс отправляет токены на те rank, где находятся выбранные router соответствующие эксперты.
- Обратная передача результатов после вычисления экспертов.

Для MoE обычно выполняются две `all_to_all`:

```
tokens
  → all_to_all: отправить токены выбранным экспертам
  → вычисление экспертов
  → all_to_all: вернуть результаты исходным процессам
```

Это одна из наиболее требовательных к коммуникационной сети операций: каждый процесс потенциально обменивается данными со всеми остальными, а размеры сообщений могут быть неравномерными из-за дисбаланса маршрутизации токенов.
#### Barrier
Barrier создаёт точку синхронизации: каждый процесс останавливается внутри вызова, пока до него не дойдут все остальные участники process group. Полезные данные между процессами при этом не передаются.

```python
dist.barrier()
```

На практике нужен реже, чем кажется. Любая другая collective operation уже синхронизирует участников, поэтому отдельный `barrier` обычно избыточен. Типичный оправданный случай — дождаться, пока rank 0 закончит запись файла, прежде чем остальные начнут его читать. И даже здесь стоит помнить, что `barrier` гарантирует только достижение точки в коде, но ничего не гарантирует про завершение асинхронных CUDA-операций.
#### Операции свёртки
Для `reduce`, `all_reduce` и `reduce_scatter` задаётся способ свёртки через `dist.ReduceOp`:

|Операция|Смысл|
|---|---|
|`SUM`|сумма (по умолчанию)|
|`AVG`|среднее (NCCL)|
|`PRODUCT`|произведение|
|`MIN` / `MAX`|минимум / максимум|
|`BAND` / `BOR` / `BXOR`|побитовые операции|
